# 架构可达性测试报告

> 目的：在继续实现前，先回答「**是否有难以实现的架构**」。
> 方法：只读探测（不登录、不提交凭据、间隔 2 秒）+ 静态资产自检 + 浏览器模型推断。
> 可复跑：`python3 tools/check_reachability.py`（默认**不发任何网络请求**；
> `--probe` 才做只读状态码探测，且不带任何账号信息）。

## 一、实测证据

| 检查 | 结果 |
|---|---|
| `site_src/local.js` / `api/reference_server.py` 语法 | OK |
| 新 CSS 外链 / CDN | 0 / 0 |
| 新 JS 外链 | 2 处，均为 `http://www.w3.org/2000/svg`（SVG 命名空间，不是网络请求）与设置框里的示例地址；CDN 0 |
| **页面加载即发 fetch** | **0**（唯一 fetch 在「探测可达性」按钮的点击回调里） |
| 当前沙盒 curl 出口：`luogu.com/article` / `/api/user/login` / `luogu.me` / `github.io` | 全部 **403**，`HTTP/2 403` 且读不到 CORS 头 |
| 浏览器真编译条件 | 无 emscripten / WASM 工具链；浏览器内无 g++ |
| Pages workflow 能力 | `setup-python` + `upload-pages-artifact` + `deploy-pages`，**纯静态托管，无服务端进程** |

### 关于「全 403」的重要区分

**这不是站点挂了，也不是频率被限，是沙盒出口策略网关的默认拒绝**（响应体
`No policy rule matched the request / policy_default_denied`）。同一时段：

- GitHub Actions 出口取洛谷文章正文为 **HTTP 200**（`azdjstpm` 8836 字节，第 15 批实证）
- 另一读取通道读 `liuyiming2024.github.io/luogu/` 返回正常 HTML（87 篇）

所以结论是「**当前这一端出不去**」，不是「目标不可达」。架构因此必须把
**取回**放 Actions、**推送**放能出网且持有登录态的一端，而不是全塞进静态站。

## 二、三个真正的难点

### 难点 1 · 静态 Pages 浏览器直推洛谷 —— 架构级不可达（硬障碍）

与新口径「评论持久化直接推洛谷」直接相关。**与 403 无关**，是浏览器模型决定：

| 障碍 | 说明 |
|---|---|
| 跨源 | Pages 域 `liuyiming2024.github.io` ≠ `www.luogu.com`，写操作触发 CORS preflight |
| 响应头 | 洛谷不返回 `Access-Control-Allow-Origin: *`，浏览器阻断响应 |
| 凭据 | 登录态是 HttpOnly + SameSite cookie，跨站 `credentials: 'include'` 带不过去 |
| CSRF | 页面 `csrf-token` 与会话绑定，静态页拿不到也用不了 |

**curl / 后端不受这四条限制，浏览器一定受。** 所以「直接推洛谷」不能用
`fetch("https://www.luogu.com/...")` 实现。

**落地形态（已实现）**：

```
文章页写评论
   ↓ 本地先存（localStorage，离线可看）→ state: 本地已存
   ↓ 待推队列（显式开关 + 配置了 apiBase 才启用）
   ↓ POST /api/comments/push-luogu   ← 交给「本机代理 / 自托管 runner / 浏览器扩展」
   ↓ 该端持有用户个人账号登录态，低频、人工确认、可一键关闭
   ↓ 洛谷文章评论区（权威持久层）
   ↓ 回写 state: 已推洛谷 / 失败待重试
```

- **洛谷 = 权威持久层；本地 = 离线镜像 + 队列**，不另建评论数据库
- 用**用户个人账号**；管理员账号（`liuyiming2024_1` / `liiyiming2024_1`）不参与评论
- 静态站代码里**没有**任何直接指向 luogu.com 的写请求
- 与「发文回推 luogu.com.cn」复用同一个适配器（`/api/publish`）

### 难点 2 · 浏览器内真编译 —— 能力级不可达

无 emscripten/WASM 工具链，浏览器没有 g++/CPython 运行时。
已用「库中 `site/data/judge_cases.json` 的 std 期望输出对照」替代本地评测，
真编译走评测 API 适配器。**不假装浏览器能编译**。

### 难点 3 · 写操作风控 —— 可达但高风险

评论 / 发文 / 回推都是**写操作**，比 GET 更容易触发风控与封号。
沿用「别给我封了」：2.0~3.5s 抖动、每 20 次小憩、50 分钟窗口 / 15 分钟静默、
403/降级长退避 30 分钟、**失败不轰炸重试**、默认关闭、仅个人账号。

## 三、不是架构障碍的几项

| 项 | 判断 |
|---|---|
| 全量 16 万篇题解 | 长期渐进，非一次搬完；`on: schedule` 自持爬取 + 断点续传已跑通 |
| 保存站刷新 | 无公开刷新接口（SPA 骨架 + 降级公告），做成可插拔 hook，不编造接口 |
| 在线取用户名/头像 | 出口 403 → 本地缓存 + 内联默认头像 + 三态颜色，已覆盖 |
| Supabase / Webnote | free 版、契约就位；当前未授权，属于「待接入」而非「做不了」 |
| 两个管理员差一个 i | 配置问题，已原样并列登记 |
| HTTP 200 的 503 错误页 / csrf 残留 | 第 16 批已修，属内容校验不属于架构 |

## 四、结论

**有难以实现的架构，且只有一处是硬的**：静态 Pages 不能自己直连洛谷做写操作。
规避方案明确、已落地为「本地队列 + 外部执行端」适配器，**不需要改目标**——
评论依然直接推洛谷、依然是权威持久层，只是发请求的不是浏览器。

其余两项（真编译、写操作风控）是能力边界与风险边界，已用替代方案和
礼貌节奏处理，不阻塞交付。

> 诚实边界：本机代理 / 自托管 runner / 评测后端**不在本仓库内运行**，
> 仓库提供的是接口契约、参考实现与前端队列。需在你自己的网络里接上才生效。
