2. 甲类 · P1421 dk5mkxij（本批唯一命中）

2.1 题解代码（按作者分段提示拼装）

文章把代码拆成 6 段给（「中间部分在下面」「循环到没钱」「买一支就扣一次钱」），按提示顺序拼成：

#include <bits/stdc++.h>
using namespace std;
int main(){
    double a,b;
    int sum=0;
    cin>>a>>b;          // a 元 b 角
    b=b/10;             // 角换算成元
    a=a+b;              // 总钱数
    while(a>=1.9){      // 循环到没钱
        a=a-1.9;
        sum++;
    }
    cout<<sum<<endl;
    return 0;
}

按「代码只是辅助、不判全不全」，拆段展示本身不是缺陷；只验拼装后的核心逻辑。

2.2 反例（题面 0≤a≤10^4, 0≤b≤9，完全合规）

输入正确实际说明
7 6437 元 6 角 = 76 角，76/19 = 4 支
19 010919 元整，190/19 = 10 支
20 91110209/19 = 11 支

独立进程复核：编译真正拼装版跑上述输入，输出与内部对拍一致。官方样例 10 3 → 5、1 9 → 1、3 8 → 2 都通过，说明不是整体逻辑错，而是恰好整除时边界比较提前 false。

全枚举：a=0..10000, b=0..9 共 100010 组，2031 组不一致。规律很清楚：当 10a+b 是 19 的倍数时，double 累减的舍入误差让最后一次 a>=1.9 判成假，少买一支。独立正确解 (10*a+b)/19（整数除法）。

2.3 划界说明（甲乙边界，写清楚免得以后翻案）

  • 事实：把比较改成 while(a>=1.9-1e-9) 后，同样 100010 组 0 不一致。
  • 仍归甲，三条理由：
  • 根因是 double 表示货币并反复累减的类型选择错误，根本修复是换成整数角运算 (10a+b)/19 —— 正对应甲类判据里的「换类型 / 重写判断」；
  • 加 eps 不是修正笔误，而是引入新的容差语义，且只对本题这个数值范围成立，换个精度/编译器不保证；
  • 作者正文明确写「把总钱数存到 a 里（所以用 double）」——是有意的设计选择，不是笔误，也不是防抄袭/乱搞形态，因此不进乙类。
  • 若你想严格按「改一处表达式即修复」的字面判据把它挪进乙，说一句我就改。
对照：同题另有多篇用整数 c=a*10+b; printf("%d",c/19); 的题解，全枚举/抽样均正确（未取到 lid，仅作内部对照，不纳入计数）。

5. 本批 3 次「差点误判」自查

#我一度以为实测处理
①P1014 某篇用 float n; int k=int(sqrt(n*2-1.75)+0.5);，n≤1e7 时 n*2 超过 float 的 2^24 尾数上限，k 会算错 → 甲类写 C++ 把 N=1..10^7 全枚举，与整数二分正确解逐项比字符串：bad=0。误差远小于 0.5，%g 也把整数值原样输出不是 hack。且该篇未取到 8 位 lid，按纪律只登记、不纳入计数
②P1003 9jadrxl0 数组开小 → 一定 REn=10021/10050 时原版照常输出正确答案，只有 n≥20000 才 SIGSEGV如实记录「部分 n 不出错」，结论仍成立但表述收紧
③P1421 dk5mkxij 是拆段给的代码，看着像「不完整」按作者 6 段提示拼装后编译通过，且缺陷在拼装后的核心逻辑里拆段不算缺陷，命中成立
