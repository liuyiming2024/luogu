全量公开资料汇集与校对 · 架构说明

目标（你的原话）：把洛谷的所有公开题面、公开题解、有用的学术文章都汇集进这个库，并且都做校对； 保存站内容可更新，爬之前先刷新一下让它重新从洛谷抓，或直接爬洛谷； 写一个大脚本做枚举与爬取、实时写回仓库、一直跑； 但不要恒定 2 秒太明显，比如每隔一个小时停上十分钟。

这份文档说明怎么落地、能到什么程度、哪些必须如实说清。

1. 先说清三件不能假装的事

  1. 全量是长期渐进，不是一次交付。 洛谷公开题解约 16 万篇量级（保存站帮助页曾提到归档 163139 篇文章），

题面数万。当前仓库是 87 个编号 / 96 篇逐篇验证。脚本是「一直跑、越攒越全」的架构， 不是「今晚搬完」。

  1. 全量自动判甲/乙/丙不可行。 三类判定需要每题写独立正确解 + 对拍 + 变异版敏感性检查，

这是逐批人工/半自动的活。脚本能做的是 L0/L1 自动校对并把条目送进 L2 待对拍队列， 不越权替你下结论。

  1. 沙盒里不能真的「一直跑」。 后台进程在工具调用之间会被回收（第 15 批实测过）。

现已按「爬取放在那边」把爬取主路径改到 GitHub Actions：crawl_tick.yml 每天 4 次错峰 tick（随机起步 + 抖动 + 降级即停），正文直接 commit 回仓库； 本地 crawl_daemon.py --forever 保留为可选补强，不再是必需。 对拍放本地（tools/verify_pipeline.py），网页放 Pages（pages.yml）。

2. 大脚本：tools/crawl_daemon.py

一个文件把「枚举 → 取回 → 校对 → 落盘 → 实时 push → 休息」串成闭环，断点续传。

2.1 有序枚举（不是遍历编号空间）

来源入队方式说明
公开题面--seed-problems 1000:1200P 号顺序推进，这才是「枚举 = 有序」
题解（已知）主表里 可逐字验证 != 是 的条目，按题号升序也可 --lids a,b,c 显式给
题解（新发现）从已取回正文里正则提取 /article/<8位>，BFS 入队，深度上限 --max-depth 2有序发现，不猜 ID
学术/规范文章8 位 ID 但无代码块、含「题解审核规范 / 算法 / 证明 / 专栏」等判据单独归类存证

绝不遍历 36⁸ 编号空间、不并发、不登录、不提交题解、不刷保存 API。 site/data/crawl_state.json 存 seen / queue / failed / 进度游标，重跑接着上次走。

2.2 保存站刷新（可插拔，不编造接口）

你说「保存站内容可以更新，爬之前先刷新一下」。落地方式：

  • 每个运行窗口开始时调一次 hook：--refresh-url <入口> 或 --refresh-cmd "<命令>"
  • 保存站没有公开刷新 API：实测首页只有导航 + 「近期有大量 AI 自动化程序不断请求保存 API,导致队列堵塞」降级公告，

/article、/articles、/square、/search、/statistics 全是 SPA 骨架，直连全 403 policy_default_denied

  • 所以不臆造接口路径；若你手上有刷新入口就注入，刷新失败也不阻塞主流程，

默认直接爬 www.luogu.com（你说的「或者你直接爬洛谷」）

  • --base 可切保存站：--base 'https://www.luogu.me/article/{lid}'

2.3 节奏：跑 50 分钟 / 歇 10 分钟（不恒定 2 秒）

参数默认作用
--run-minutes / --rest-minutes50 / 10每个小时歇十分钟，窗口结束静默后再开新窗口
--delay / --jitter2.0 / 1.5每次间隔在 2.0~3.5 秒随机抖动，不是固定 2 秒
--micro-batch / --micro-rest20 / 30s每 20 次请求小憩 ~30 秒（带 ±30% 抖动）
--daily-cap2000每日总请求上限，到点提前收工
--cooldown1800403/429/5xx/降级公告 → 长退避 30 分钟、本窗口提前结束
--max-hours / --max-requests0(不限)总时长 / 总请求上限

即：不是匀速爬，是「有抖动的小批 + 微憩 + 整段休息」。固定 UA、单并发， 命中「服务降级公告 / Request denied / 队列堵塞」立即停本轮，不给站点添负担。

2.4 实时写回仓库

  • 每 --push-every 10 篇或每 --push-interval 600 秒：git add → commit → pull --rebase → push
  • 写回内容：site/data/ingested/<id>.json（正文）、crawl_state.json、

取回日志.jsonl、校对台账.csv、爬取进度.md、verify_queue.jsonl

  • token 只从环境变量 GITHUB_TOKEN 读，不进仓库、不写 .git/config
  • 每个窗口结束重生成 _build_site.py（选择性清理，不会删 ingested 与常驻脚本）
  • concurrency 组保证同一时刻只有一个 crawl run

3. 校对分三层

层做什么自动？
L0 编目判定8 位 ID 格式、是否题解 / 题面 / 学术规范文章、题号与 URL 一致、SPA 骨架识别✅
L1 内容校对代码块提取（<pre>）、sha256 去重留证、可选 -fsyntax-only 编译预检（CE 只登记、不算 hack）、证据落盘✅
L2 三类判定写进 site/data/verify_queue.jsonl，等逐批「独立正确解 + 对拍 + 变异版敏感性检查」后定甲/乙/丙❌ 排队，不越权

02_文章编号索引/校对台账.csv 每条都带 L0/L1 结果、sha256、证据路径、L2 状态， 离线也能查「这条有没有被核过、凭什么」。

题面页会摘录「题目描述 / 输入格式 / 说明·数据范围」进索引， 正是后续对拍判断反例是否合规（题面内）的依据——这是「校对」里最值钱的一层。

4. Actions 是自主主路径（不需要人工触发）

2026-11-25 更正：仓库已由私有改为公开。官方计费文档明确 「标准 GitHub 托管运行器在公共仓库中免费、不计分钟」，私有仓库 GitHub Free 的 2000 分钟/月额度不再适用。此前「50 分钟/小时会烧光额度」 的估算是私有口径，已作废。
项现在的配置
触发on: schedule —— GitHub 自己的调度器，不看对话、不需要我或你按 dispatch
频率每 2 小时一个错峰窗口（UTC 奇数小时第 23 分，避开整点高负载）
窗口随机起步 0~150s → 45 分钟爬取 → 窗口间天然静默 15 分钟
单次上限200 请求；每日 2000 请求硬上限；403/降级长退避 30 分钟
断点续传site/data/crawl_state.json，丢一次 run 也不丢进度
实时写回每 50 篇或窗口末 commit + push，重生成署名与离线站
队列自续主表无正文题解按题号升序补入；题面连续骨架降为每轮 1 个探测

仍然存在的平台限制（不是钱的问题）：单个 runner 是临时 VM，job 结束即销毁； 单 job 最长 6 小时；GITHUB_TOKEN 最多 24 小时；schedule 最短每 5 分钟一次， 高负载时可能延迟甚至丢弃某次 run（官方建议错开整点）；公开仓库 60 天无 「仓库活动」会自动禁用 schedule，且 cron 自身运行不算活动。

对应加固：

  • crawl_tick.yml 的「有效产出校验」步骤：job 全绿但全部只拿到 SPA 骨架时会

写 ::warning:: 并留痕，杜绝第 1 次那种「静默空转」

  • .github/workflows/keepalive.yml：每周一次极小提交刷新活动时钟，防止 60 天后

定时工作流被静默关掉

  • concurrency 组保证同一时刻只有一个爬取 job，不打断正在写回的进程
  • 丢一次 run 无所谓：state 断点续传，下一个窗口接着队列走

tools/crawl_daemon.py --forever（跑 50 / 歇 10）保留为可选补强： 在你自己的机器上它才是真正的常驻进程，不受 6 小时上限与 cron 抖动影响。 但不再必需——没人盯着时，Actions 这条链自己会跑。

5. 怎么开始

# 1) 冒烟（不发包、不推送，验证状态机）
python3 tools/crawl_daemon.py --dry-run --max-requests 3 --run-minutes 1 --rest-minutes 0

# 2) 本地长期跑：50 分钟跑 / 10 分钟歇，P1000 起顺序灌 200 个题面
export GITHUB_TOKEN=你的token
python3 tools/crawl_daemon.py --forever \
    --seed-problems 1000:1200 \
    --delay 2.0 --jitter 1.5 \
    --push-every 10

# 3) 如果有保存站刷新入口
python3 tools/crawl_daemon.py --forever \
    --refresh-url 'https://你的刷新入口' \
    --base 'https://www.luogu.me/article/{lid}'

# 4) 随时看进度
cat 02_文章编号索引/爬取进度.md
python3 _build_site.py && 双击 site/index.html

闭环：

Actions 错峰 tick（随机起步 + 抖动 + 降级即停）
  → 有序队列（P号顺序 / 主表待补 / 正文 BFS 发现 ID）
  → L0 判定 + L1 校对留证 + L2 排队
  → 每10篇实时 commit/push 回仓库
  → 每窗口重生成离线站
  → 本地 tools/verify_pipeline.py 消费 verify_queue.jsonl 做三类对拍
  → 结果写回 article_index.csv / 批次报告 / 站点

7. 公开、版权与署名（2026-11-24 追加）

仓库已按归档者意见改为公开并上线 GitHub Pages 归档库网页。 每条收录内容由 tools/provenance.py 生成原文链接 / 作者署名 / 取回时间 / sha256 内容完整性签名 / 可复制引用格式，渲染进每篇文章页的「引用与署名」块。 pages.yml 部署前会校验「署名条目数 == 收录总数」且无缺项。 版权归原作者及洛谷所有，不用于商业用途，权利人可申请移除； 详见 00_总览/归档与版权声明.md。

8. 审查与防回归（第 16 批追加）

爬取链自动化之后，风险从「跑不跑」变成「跑出来的东西对不对」。tools/verify_infra.py 提供两层校验，不发网络请求、全用受控夹具：

  • Part A 逐篇审查 site/data/ingested/：原文链接、代码块可提取、sha 唯一、

csrf/凭据/邮箱残留、503 错误页与 SPA 骨架不得存档、provenance 署名与签名覆盖

  • Part B 类对拍：13 个检查点，每个同时跑真实实现与变异实现，

变异没被抓到即判空跑（与题解对拍同一纪律）

pages.yml 在部署前执行 python3 tools/verify_infra.py --check，失败即阻断部署。 报告：02_文章编号索引/基础设施审查与验证报告.md； 机器可读：05_对拍原始数据/基础设施验证结果.json。

本轮实际修掉的三个真问题

  1. 匿名页面令牌：洛谷页面带一次性 csrf-token meta，公开仓库不该留。

取回即 sanitize_body()，历史 85 篇回填；正文与 <pre> 逐字不动。

  1. 只认 C++ 的判定：Python / Pascal / 伪代码题解被归成「学术/题解文字」。

extract_code() 改为先取 <pre> 再按多语言特征判定。

  1. HTTP 200 不等于正文：限流时洛谷返回 200 + 「503 - 洛谷日爆」错误页，

旧逻辑当题面存档了 5 份。503 特征进 STOP_MARKERS，命中长退避。

纪律：状态码、job 是否变绿、文案里有没有「已移除」，都不能当作内容正确的证据； 必须看响应体本身。
